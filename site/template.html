How it works

A grader is only as good as the wrong answers it rejects. So every task ships with some.

01

A real ticket

A runnable starter repo with the feature missing, and a ticket that states every rule: rounding mode, minor units, time zone, error codes.

Make payment creation idempotent
02

Five solutions

A reference, a correct alternative written a different way, and three wrong answers a capable engineer could plausibly write.

referencealt_validwrong_retry_racewrong_key_scopewrong_inmemory_cache
03

A naive grader

Written first and committed first: the happy path, the ticket's own example and one obvious edge case. Then measured.

04

A hardened grader

Targeted tests are added until every wrong answer fails for its declared reason, while both correct solutions keep passing.

Worked example · task 01

Two retries, one moment, two charges. The quick grader never sees it.

  1. The ruleThe ticket says concurrent duplicates must charge exactly once. It says nothing about how.
  2. The plausible bugLook up the key, charge the card, then save the key. It's what most people write first, and every sequential retry works.
  3. Why the naive grader passes itIt retries one request after another. The first response is already saved, so the second is replayed and nothing looks wrong.
  4. How the hardened grader catches itTen callers wait at a barrier and fire together against a live server, with a 150 ms card network so the race window is wide. 25 rounds, one charge each.

Fine print

    

    
All tasks, accounts, merchants and file formats are synthetic. No real bank, customer or system is represented. The solutions are an author-written sample, not observed model output, and the blind reviews so far are self-reviews. Same-host subprocess isolation is for reproducibility, not a security boundary.
