PROBLEM.md

# Ticket: payment retries must be idempotent

Our synthetic payment service already charges a declared gateway and returns a receipt.
Clients retry requests after losing a response. Implement the following observable contract.

Public interface: `app.main.create_app(database_url: str, gateway: Gateway) -> FastAPI`;
`app.gateway.Gateway.charge(merchant_id, amount_minor, currency, source_token) -> ChargeResult`.
`ChargeResult(charge_id: str, status: "succeeded"|"declined")` is a frozen dataclass.
The starter also exports `app.gateway.FakeGateway` for visible and naive smoke tests;
its `.calls` property is a tuple of charging calls. Hidden final tests inject their own Gateway.
`POST /v1/payments` takes `X-Merchant-Id`, `Idempotency-Key`, and JSON
`{amount_minor, currency, source_token}`. Money is positive integer minor units, never bool.
Currencies supported: CAD/USD/EUR/GBP (2 dp), JPY (0), KWD/BHD (3). No conversion occurs.

- Key required, length 1–255 characters; missing/empty/too long: HTTP 400
  `idempotency_key_required`. Merchant is a nonempty string; missing: 400 `merchant_required`.
- Invalid JSON body/fields: 422 `invalid_payment`. Ignore JSON member ordering. Body equality
  means equality of the three validated fields; no extra fields are accepted.
- Keys are scoped per merchant. Same merchant, key and body replay the original status and JSON
  exactly, without another gateway call. Declines (402 `card_declined`) also replay exactly.
- Same merchant and key with a different body: 422 `idempotency_key_reuse`, no charge,
  whether the first request is complete or in flight.
- Concurrent identical duplicates cause exactly one gateway charge. Each duplicate either gets
  the original response or HTTP 409 `idempotency_request_in_progress`. A later retry must replay.
- This behavior survives creating another app instance against the same database; no expiry.
- A successful receipt is HTTP 201 with `payment_id`, `charge_id`, `status` ("succeeded"),
  `amount_minor`, `currency`, and `merchant_id`. The payment id is nonempty and unique for distinct
  payments. Do not compare an id to any particular UUID format.
- Errors are JSON `{"error":{"code":"<snake_case>","message":"..."}}`; message text is free.
  No gateway exceptions or crash recovery are in scope. A charge returns normally with either status.

Preserve the factory and gateway protocol. Store state in the supplied PostgreSQL database;
the application may create its own schema. Tests inspect only the declared HTTP surface and
gateway calls. Timestamps in stored receipts use aware UTC; no timestamp field is required in JSON.
Run visible tests from starter: `python -m pytest tests -q` with `DATABASE_URL` set to a disposable
database. No customer data or real payment network is involved.

PROBLEM.md

# Ticket: accrue interest across partial calendar months

The synthetic CAD account needs correct daily accrual and explicit posting boundaries.
Keep `interest.accrual.accrue(principal: Decimal, annual_rate: Decimal, start: date, end: date,
method: Literal["simple_monthly","daily_compound"]) -> list[Posting]` and
`Posting(posting_date: date, interest: Decimal, balance: Decimal)` (frozen dataclass).

CAD has 2 decimal places. Principal is a nonnegative finite Decimal in whole cents; rate is
a nonnegative finite Decimal (a fraction, e.g. 0.05 means 5%). Invalid values/method or end before
start raise ValueError. These are dates, not timestamps; any datetime instead of date is invalid.

- Day count is Actual/365 Fixed, including leap years. Accrue for every date in `[start,end)`.
- Post on each month end within that period, and also on `end - 1 day` if it is not a month end.
  Return chronological postings. `start == end` returns `[]`.
- `simple_monthly`: interest at a posting equals current posted balance × rate × segment days / 365.
  Add each posting to the balance; thus it compounds at posting boundaries.
- `daily_compound`: each date, accrued += (posted balance + accrued) × rate / 365 with full
  intermediate precision. At posting, round accrued, add to balance, reset accrued to zero;
  discard the unrounded residual.
- Round only the posting to 0.01 using ROUND_HALF_EVEN. Intermediate arithmetic must use
  precision at least 28 or exact arithmetic. Both money fields must be Decimal with exponent -2,
  even when zero. Return the resulting balance after each posting.

Worked example: principal 1000.00, rate 0.0365 (so 0.0001 per day), start 2026-01-01, end 2026-03-01.
Both methods post on 2026-01-31 (31 days) and 2026-02-28 (28 days). January: 1000.00 x 0.0365 x 31 / 365 =
3.10, balance 1003.10. February: 1003.10 x 0.0365 x 28 / 365 = 2.8087..., posted as 2.81, balance 1005.91.
(With `daily_compound` the unrounded January interest is 3.1048...; both methods round to the same cents here.)

Only the declared interface is graded; internal representation and algorithms are unrestricted.
Run from starter: `python -m pytest tests -q`. All examples and accounts are synthetic.

PROBLEM.md

# Ticket: enforce the journal invariant

`ledger.service.LedgerService(database_url)` operates a synthetic PostgreSQL ledger.
Expose frozen `Line(account_code: str, side: "debit"|"credit", amount_minor: int)` and:
`create_account(code,currency)`, `post(lines: list[Line],memo: str)->int`,
`reverse(txn_id:int,memo:str)->int`, `balance(account_code)->int`,
`trial_balance()->dict[str,tuple[int,int]]`.

Money uses integer minor units. Currencies: CAD/USD/EUR/GBP=2 dp, JPY=0, KWD/BHD=3;
no exchange or cross-currency netting. Errors derive from LedgerError:
UnbalancedTransaction, InvalidAmount, UnknownAccount, AlreadyReversed, CannotReverseReversal.

- A post has at least two lines (otherwise UnbalancedTransaction). Each amount is a positive
  int, never bool (otherwise InvalidAmount). Side must be debit or credit (LedgerError).
- All accounts must exist (UnknownAccount). For EACH currency independently, sum of debits
  equals sum of credits (otherwise UnbalancedTransaction).
- Posting is atomic. Every rejected operation leaves balances and trial balance unchanged,
  including a missing account after other valid lines. Inputs are not mutated.
- Balance is debits minus credits. trial_balance keys are all currencies of created accounts,
  values are `(total_debits,total_credits)` across all posted lines, including reversal lines.
  A currency without postings has `(0,0)`. balance of an unknown account raises UnknownAccount.
- reverse creates a new transaction, with every side swapped, links it to the original and
  returns its distinct id. An original can be reversed at most once (AlreadyReversed).
  A reversal itself cannot be reversed (CannotReverseReversal). An unknown txn raises LedgerError.
  Reversal counts as real debit/credit turnover; it does not erase original lines.
- State survives constructing a new service. Re-creating an account with the same code and
  currency is idempotent; different currency, empty code or unsupported currency -> LedgerError.
- Validation priority: line count, amount/side, accounts, balancing. On reversing a reversal,
  CannotReverseReversal takes priority. Memo is arbitrary synthetic text.

Worked example (CAD accounts `cash` and `revenue`, synthetic):
`post([Line("cash","debit",5000), Line("revenue","credit",5000)], "sale")` returns id 1;
afterwards `balance("cash") == 5000`, `balance("revenue") == -5000` and `trial_balance()["CAD"] == (5000, 5000)`.
`reverse(1, "undo sale")` returns a different id; both balances are then 0 and the CAD trial balance is
`(10000, 10000)`. Reversing id 1 again raises AlreadyReversed.

The service may create its own tables; tests observe only the declared methods. Run
`python -m pytest tests -q` from starter with DATABASE_URL pointing at a disposable database.

PROBLEM.md

# Ticket: available balance must include active holds

`holds.main.create_app(database_path,clock)->FastAPI` uses SQLite. The declared
`holds.clock.Clock` Protocol has `now()->datetime`, always aware (otherwise ValueError).
The factory seeds two synthetic accounts on first use, without resetting existing state:
`acct_standard`: posted10000, overdraft0; `acct_flex`: posted10000, overdraft5000.
All money is integer CAD minor units (2 dp). All amounts must be positive ints, never bool.

- GET /accounts/{id}/balance ->200 `{posted_minor,available_minor}`.
  available = posted minus sum of active, unexpired holds.
- POST /accounts/{id}/authorizations `{amount_minor}` ->201 `{auth_id}` iff amount <=
  available + that account's overdraft limit; otherwise402 `insufficient_funds` with no effect.
- A hold expires exactly 7×24 hours after creation, and stops counting at that instant.
- POST /authorizations/{id}/capture `{amount_minor}`: amount <= held amount; overcapture ->422
  `capture_exceeds_hold` with no effect. Successful capture ->200 `{auth_id,status:"captured"}`,
  deduct amount from posted balance, close the hold and release ALL unused remainder.
- POST /authorizations/{id}/void ->200 `{auth_id,status:"voided"}`, close hold, no posted change.
- Capturing/voiding an expired or already closed hold ->409 `authorization_closed`, no effect.
- Invalid body/amount ->422 `invalid_amount`; unknown account/auth ->404 `not_found`.
  Errors are `{"error":{"code":"...","message":"..."}}`; message text is free.
  Validate amount before closed status for capture. Void has no JSON body.
- Auth ids are nonempty unique strings; available may be negative within overdraft.
  State survives creating another app on the same file. Operations are atomic and per account.

Worked example (`acct_standard`, CAD minor units): authorize 3000 -> 201 and the balance is
`{posted_minor: 10000, available_minor: 7000}`. Capture 1200 -> 200 and the balance is
`{posted_minor: 8800, available_minor: 8800}`: the 1200 is deducted from posted and the unused 1800 of the
hold is released. A further authorization of 8801 is declined with 402 `insufficient_funds`; 8800 is approved.

Tests use the HTTP interface and the injected clock only. No real accounts, system clock delays
or network payments. Run `python -m pytest tests -q` from starter.

# Ticket: monthly statements follow the account timezone

`statements.period.period_bounds(account_tz:str,year:int,month:int)->tuple[datetime,datetime]`
returns aware UTC instants for a half-open interval. `select(txns:list[Txn],account_tz,year,month)`
returns transaction ids sorted by instant, then lexicographic id. Frozen `Txn(id:str,at:datetime)`
is public. IDs are unique and timestamps may have arbitrary aware offsets and microseconds.

The period is the calendar month in the account's IANA timezone: local 00:00 on day 1 inclusive
through local 00:00 on day 1 of the next month exclusive, converted to UTC using zoneinfo.
An unknown time zone name, a non-int (or bool) year or month, a month outside 1-12 or a year outside
1900-2098 raises ValueError from both functions. Daylight saving rules apply independently to both
endpoints. Each input timestamp must be aware with a non-None utcoffset,
otherwise select raises ValueError, even when that transaction would be outside the month.
Do not mutate inputs. Empty input returns []. Money is not part of this interface.

Worked example: for an `America/Toronto` account, January 2026 is the interval
`[2026-01-01T05:00:00Z, 2026-02-01T05:00:00Z)` (Toronto is UTC-5 in January). A transaction at
`2026-02-01T04:30:00Z` is 23:30 on 31 January in Toronto, so it belongs to January; one at
`2026-02-01T05:30:00Z` is 00:30 on 1 February and belongs to February. So selecting January 2026 for
`Txn("a", 2026-02-01T04:30Z)` and `Txn("b", 2026-02-01T05:30Z)` returns `["a"]`.

Run from starter: `python -m pytest tests -q`. The records are entirely synthetic.

refund amount may not exceed the captured amount, which may be less than authorized. Exceeding
remaining captured funds -> RefundExceedsCaptured. Rejected attempts must never count toward
refunded_total or reduce the future budget. Validate positive amount before capture status.

on the same file. Operations are atomic; no rejected operation may alter successful totals.

`refunded_total(id) == 4000`. `refund(id, 2500)` then raises RefundExceedsCaptured, because only 2000 of the
captured 6000 remains, and `refunded_total(id)` is still 4000.

PROBLEM.md

# Ticket: price the whole payment at its selected tier

`fees.schedule.compute_fee(amount_minor:int,schedule:Schedule)->int` returns integer minor units.
Public frozen dataclasses: `Tier(up_to_minor:int|None,bps:int,fixed_minor:int)` and
`Schedule(tiers:list[Tier],min_fee_minor:int,max_fee_minor:int)`.

Amounts are nonnegative ints, never bool; negative/noninteger -> ValueError. Schedule tiers are
ordered by strictly increasing nonnegative upper bounds, ending with exactly one None (infinity).
Bps/fixed/min/max are nonnegative ints, min <= max. `compute_fee` raises ValueError for an invalid
schedule (checked on every call, whatever the amount).

- Select the FIRST tier where amount <= up_to_minor, or None. Upper bounds are INCLUSIVE.
- Pricing is non-marginal: apply that selected tier's bps to the ENTIRE amount, then add its
  fixed fee. Do not sum bands.
- Raw fee = amount × bps / 10000 + fixed_minor. Round once to an integer using ROUND_HALF_UP,
  then clamp to [min_fee_minor,max_fee_minor]. This deliberately differs from interest's half-even.
- Zero amounts still incur the selected fixed fee, subject to the clamp. Input schedules are not
  mutated. The currency is implicit; all numbers use the same minor unit (e.g. CAD has 2 dp).

Worked example: tiers `[Tier(10000, 100, 10), Tier(20000, 50, 20), Tier(None, 25, 30)]` with
`min_fee_minor=25`, `max_fee_minor=100`. An amount of 5000 uses the first tier: 5000 x 100 bps = 50, plus 10, so 60.
An amount of 15000 uses the second tier on the whole amount: 75 + 20 = 95. An amount of 100 would cost 11
and is raised to the minimum, 25. An amount of 30000 would cost 75 + 30 = 105 and is capped at 100.

Run from starter: `python -m pytest tests -q`. No real fees, networks or institutions are represented.

PROBLEM.md

# Ticket: validate invented SBF-80 batch files atomically

`batch.parser.parse(data:bytes)->BatchResult` returns frozen dataclasses exported from that module:
`Payment(payee_account:str,amount_minor:int,reference:str)`, `BatchError(line_no:int,code:str)`,
`BatchResult(accepted:bool,payments:list[Payment],errors:list[BatchError])`.

SBF-80 is invented for this synthetic task. Each record is exactly 80 printable ASCII characters,
followed by LF or CRLF. A final terminator is optional; mixed LF/CRLF is accepted. Strip the
terminator before checking width and slicing. Interior blank lines are records and invalid.
Bare CR, non-ASCII or control bytes are invalid_encoding. All positions below are 1-based inclusive.

| Record | Columns | Field |
|---|---|---|
| H | 1 | H |
| H | 2–13 | batch id: 12 uppercase ASCII letters/digits |
| H | 14–21 | creation date YYYYMMDD, valid calendar date |
| H | 22–24 | currency CAD, USD, EUR, GBP, JPY, KWD or BHD |
| H | 25–80 | spaces |
| D | 1 | D |
| D | 2–13 | 12 ASCII digits, payee account (retain leading zeros) |
| D | 14–25 | 12 ASCII digits, positive zero-padded integer minor units |
| D | 26–45 | 20 printable chars, nonblank reference, right-space padded |
| D | 46–80 | spaces |
| T | 1 | T |
| T | 2–7 | detail count, 6 ASCII digits |
| T | 8–22 | control total of amounts, 15 ASCII digits |
| T | 23–32 | hash total, 10 ASCII digits |
| T | 33–80 | spaces |

Exactly one header first, then one or more details, then exactly one trailer last. The count is
the number of D records, including malformed D records. Control total and hash total use only
fully valid detail records. Hash = sum(int(last 8 digits of each payee account)) mod 10**10.
Money is in header-currency minor units: CAD/USD/EUR/GBP=2 dp, JPY=0, KWD/BHD=3. Do not convert.
Returned references remove right padding only. Preserve detail order and account strings.

Any error rejects the whole batch: accepted=False and payments=[]. Report all detectable errors,
deduplicated by (line_no,code), sorted by line_no then code. Continue checking other records.
For a wrong-width or invalid-encoding record, report only that local error (no field errors),
but structural/order and trailer comparisons can still be reported. Field errors are one code per
record even if multiple fields are invalid. Trailer totals compare independently when its fields
are valid, even if other records failed.

Codes: invalid_encoding, line_length, record_type, record_order, invalid_header, invalid_detail,
invalid_trailer, count_mismatch, control_total_mismatch, hash_total_mismatch, missing_header,
missing_trailer. H outside first position, T outside last, or D at first/last -> record_order.
Unknown type -> record_type. A missing first H -> missing_header at line1; missing final T ->
missing_trailer at the last line (line1 for empty input). An empty detail section -> count_mismatch
on the trailer. Header/trailer field errors include invalid reserved spaces. No other codes.

Worked example (each record is padded with spaces to 80 characters; trailing spaces are not shown):

```text
HSYNTHBATCH0120260115CAD
D000000012345000000010000INV-2026-001
D000000067890000000002550INV-2026-002
T0000020000000000125500000080235
```

The batch is accepted with two payments: `Payment("000000012345", 10000, "INV-2026-001")` and
`Payment("000000067890", 2550, "INV-2026-002")`. Count 2; control total 10000 + 2550 = 12550; hash total
12345 + 67890 = 80235. Changing the trailer count to `000003` rejects the whole batch with
`BatchError(4, "count_mismatch")` and `payments == []`.

Run from starter: `python -m pytest tests -q`. No real batch format, institution or customer is used.
