PROBLEM.md

# Ticket: payment retries must be idempotent

Our synthetic payment service already charges a declared gateway and returns a receipt.
Clients retry requests after losing a response. Implement the following observable contract.

Public interface: `app.main.create_app(database_url: str, gateway: Gateway) -> FastAPI`;
`app.gateway.Gateway.charge(merchant_id, amount_minor, currency, source_token) -> ChargeResult`.
`ChargeResult(charge_id: str, status: "succeeded"|"declined")` is a frozen dataclass.
The starter also exports `app.gateway.FakeGateway` for visible and naive smoke tests;
its `.calls` property is a tuple of charging calls. Hidden final tests inject their own Gateway.
`POST /v1/payments` takes `X-Merchant-Id`, `Idempotency-Key`, and JSON
`{amount_minor, currency, source_token}`. Money is positive integer minor units, never bool.
Currencies supported: CAD/USD/EUR/GBP (2 dp), JPY (0), KWD/BHD (3). No conversion occurs.

- Key required, length 1–255 characters; missing/empty/too long: HTTP 400
  `idempotency_key_required`. Merchant is a nonempty string; missing: 400 `merchant_required`.
- Invalid JSON body/fields: 422 `invalid_payment`. Ignore JSON member ordering. Body equality
  means equality of the three validated fields; no extra fields are accepted.
- Keys are scoped per merchant. Same merchant, key and body replay the original status and JSON
  exactly, without another gateway call. Declines (402 `card_declined`) also replay exactly.
- Same merchant and key with a different body: 422 `idempotency_key_reuse`, no charge,
  whether the first request is complete or in flight.
- Concurrent identical duplicates cause exactly one gateway charge. Each duplicate either gets
  the original response or HTTP 409 `idempotency_request_in_progress`. A later retry must replay.
- This behavior survives creating another app instance against the same database; no expiry.
- A successful receipt is HTTP 201 with `payment_id`, `charge_id`, `status` ("succeeded"),
  `amount_minor`, `currency`, and `merchant_id`. The payment id is nonempty and unique for distinct
  payments. Do not compare an id to any particular UUID format.
- Errors are JSON `{"error":{"code":"<snake_case>","message":"..."}}`; message text is free.
  No gateway exceptions or crash recovery are in scope. A charge returns normally with either status.

Preserve the factory and gateway protocol. Store state in the supplied PostgreSQL database;
the application may create its own schema. Tests inspect only the declared HTTP surface and
gateway calls. Timestamps in stored receipts use aware UTC; no timestamp field is required in JSON.
Run visible tests from starter: `python -m pytest tests -q` with `DATABASE_URL` set to a disposable
database. No customer data or real payment network is involved.

- `simple_monthly`: interest at a posting equals current posted balance × rate × segment days / 365.

All money is integer CAD minor units (2 dp). All amounts must be positive ints, never bool.

- GET /accounts/{id}/balance ->200 `{posted_minor,available_minor}`.
  available = posted minus sum of active, unexpired holds.
- POST /accounts/{id}/authorizations `{amount_minor}` ->201 `{auth_id}` iff amount <=
  available + that account's overdraft limit; otherwise402 `insufficient_funds` with no effect.
- A hold expires exactly 7×24 hours after creation, and stops counting at that instant.

  `capture_exceeds_hold` with no effect. Successful capture ->200 `{auth_id,status:"captured"}`,
  deduct amount from posted balance, close the hold and release ALL unused remainder.
- POST /authorizations/{id}/void ->200 `{auth_id,status:"voided"}`, close hold, no posted change.

- Invalid body/amount ->422 `invalid_amount`; unknown account/auth ->404 `not_found`.
  Errors are `{"error":{"code":"...","message":"..."}}`; message text is free.

otherwise select raises ValueError, even when that transaction would be outside the month.

followed by LF or CRLF. A final terminator is optional; mixed LF/CRLF is accepted. Strip the
terminator before checking width and slicing. Interior blank lines are records and invalid.
Bare CR, non-ASCII or control bytes are invalid_encoding. All positions below are 1-based inclusive.

| Record | Columns | Field |
|---|---|---|
| H | 1 | H |
| H | 2–13 | batch id: 12 uppercase ASCII letters/digits |
| H | 14–21 | creation date YYYYMMDD, valid calendar date |
| H | 22–24 | currency CAD, USD, EUR, GBP, JPY, KWD or BHD |
| H | 25–80 | spaces |
| D | 1 | D |
| D | 2–13 | 12 ASCII digits, payee account (retain leading zeros) |
| D | 14–25 | 12 ASCII digits, positive zero-padded integer minor units |
| D | 26–45 | 20 printable chars, nonblank reference, right-space padded |
| D | 46–80 | spaces |
| T | 1 | T |
| T | 2–7 | detail count, 6 ASCII digits |
| T | 8–22 | control total of amounts, 15 ASCII digits |
| T | 23–32 | hash total, 10 ASCII digits |
| T | 33–80 | spaces |

Exactly one header first, then one or more details, then exactly one trailer last. The count is
the number of D records, including malformed D records. Control total and hash total use only
fully valid detail records. Hash = sum(int(last 8 digits of each payee account)) mod 10**10.
Money is in header-currency minor units: CAD/USD/EUR/GBP=2 dp, JPY=0, KWD/BHD=3. Do not convert.
Returned references remove right padding only. Preserve detail order and account strings.

Any error rejects the whole batch: accepted=False and payments=[]. Report all detectable errors,
deduplicated by (line_no,code), sorted by line_no then code. Continue checking other records.
For a wrong-width or invalid-encoding record, report only that local error (no field errors),
but structural/order and trailer comparisons can still be reported. Field errors are one code per
record even if multiple fields are invalid. Trailer totals compare independently when its fields
are valid, even if other records failed.

Codes: invalid_encoding, line_length, record_type, record_order, invalid_header, invalid_detail,
invalid_trailer, count_mismatch, control_total_mismatch, hash_total_mismatch, missing_header,
missing_trailer. H outside first position, T outside last, or D at first/last -> record_order.
Unknown type -> record_type. A missing first H -> missing_header at line1; missing final T ->
missing_trailer at the last line (line1 for empty input). An empty detail section -> count_mismatch
on the trailer. Header/trailer field errors include invalid reserved spaces. No other codes.
